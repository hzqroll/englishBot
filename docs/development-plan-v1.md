## 1. 目标与交付范围

第一版开发目标不是一次性把全部想法做满，而是在现有项目基础上，稳定交付一个可持续运行的“群内英语训练营机器人”。

V1 最终要交付的核心能力：

- 07:30 自动生成并推送每日学习包
- 白天全量采集群内发言，并为晚间总结准备学习证据
- `@机器人` 提供翻译、英文纠错、表达润色与错误沉淀
- 18:00 自动推送个人错误整理卡
- 20:00 自动推送个人学习进度卡
- 次日回捞机制，确保前一日高价值内容再次激活
- 周报与周测的基础闭环
- 后台可管理群号、查看用户与配置、手动触发关键任务

## 2. 开发策略

开发策略采用“先底座、后内容、再闭环、最后运营”的顺序，避免一开始同时改动所有层：

1. 先稳住数据底座和群聊采集
2. 再做每日学习包与次日回捞
3. 再把 18:00 / 20:00 晚间闭环接完整
4. 最后补周报、周测和后台运营能力

执行原则：

- 每个阶段都必须有可运行、可验证的交付物
- 每个阶段都要保证现有 `@机器人` 主链路不回退
- 数据模型先扩展，功能再消费这些数据
- 文本降级永远存在，不让卡片渲染失败阻断主功能

### 2.1 验证机制

第一版开发过程中，验证不是收尾动作，而是每个阶段的固定交付物。

每个阶段都必须同时交付以下 5 类验证：

- 静态验证
  - 代码可编译
  - 模板可加载
  - 类型或导入关系不报错
- 自动化验证
  - 新增或更新对应的 `pytest` 测试
  - 至少覆盖新增逻辑的主路径和一个失败/降级路径
- 数据验证
  - 涉及表结构时，必须验证迁移可执行
  - 涉及快照、证据、卡片、日志写入时，必须验证数据库中的实际落库结果
- 集成验证
  - 至少用 `FastAPI TestClient` 或等效方式验证一条完整链路
  - 涉及消息发送时，至少验证到生成 `MessageEnvelope`、卡片快照或发送日志
- 人工验收
  - 对后台页面、卡片样式、群消息联调等体验型改动，必须补一次人工检查

每个阶段的完成定义固定为：

- 功能代码完成
- 对应文档或 Todo 已更新
- 验证清单勾选完成
- 有可回看的验证证据

推荐保留的验证证据：

- 命令输出摘要
- 数据库查询结果摘要
- 卡片渲染图片或预览文件
- 后台页面访问状态码
- OneBot/NapCat 日志中的关键成功记录

### 2.2 通用验证基线

所有后续阶段默认至少执行以下基线验证：

- 静态检查
  - `python3 -m py_compile $(find src tests -name '*.py')`
- 自动化测试
  - `uv run pytest`
- 路由/后台冒烟
  - 登录后台
  - 访问受影响页面
  - 对关键 POST 行为做一次提交验证
- 数据库验证
  - 若改 schema，执行 `alembic upgrade head`
  - 若改快照/日志写入，验证至少一条真实落库记录

新增功能如果无法在本地做完整 QQ 联调，至少要做到：

- 本地 TestClient 链路通过
- 关键数据落库通过
- 降级路径可触发

## 3. 里程碑规划

### M0. 基线整理

目标：

- 把当前仓库从“原型状态”整理到适合继续扩展的基线

交付物：

- 文档齐全
- 后台 UI 可用
- 学习群管理可修改群号
- 当前 `@机器人`、图片卡片、定时任务主链路可继续运行

完成标准：

- 文档入口清晰
- 管理后台可登录、可修改群号
- 当前群消息链路不报错

### M1. 数据底座与群聊观察

目标：

- 让系统具备“全量观察群聊并存储分析材料”的能力

交付物：

- 扩展 `message_events`
- 新增 `conversation_evidences`
- 新增被动群消息观察插件
- 基础学习证据提取逻辑

完成标准：

- 已启用群内的普通文本消息能够入库
- 能区分普通群聊、命令、`@机器人`
- 能识别英语尝试、目标词命中等基础证据

### M2. 每日学习包与词库系统

目标：

- 每天 07:30 稳定生成一份可读、可练的学习包

交付物：

- 静态 BEC 词库与主题库
- 每日选词规则
- 每日学习包生成逻辑
- 学习包图片卡片
- `daily_target_items` 落库

完成标准：

- 每天能生成 `5 个核心词块 + 5 个支持词汇 + 1 段情景对话 + 2-3 个任务`
- 学习包结果可追溯、可重发

### M3. 次日回捞与复习强化

目标：

- 让“昨天学的内容”在今天再次被使用，而不是学完即丢

交付物：

- `review_candidates`
- 次日回捞选点规则
- 学习包顶部“昨日回顾”
- 今日任务内嵌回捞要求
- 20:00 卡片里的“昨日回捞表现”

完成标准：

- 每日能从前一日自动选出 3 个回捞点
- 至少 1 个任务要求复用昨日内容
- 晚间能展示回捞结果

### M4. 晚间闭环

目标：

- 让 18:00 / 20:00 成为真正有学习价值的复盘节点

交付物：

- `daily_learning_snapshots`
- `daily_card_snapshots`
- 18:00 错误整理卡生成逻辑
- 20:00 学习进度与掌握度卡生成逻辑
- 学习掌握度模型提示词与证据引用规范

完成标准：

- 只给报名用户发卡
- 卡片基于当天真实学习证据
- 掌握度判断有可解释依据

### M5. 周报、周测与运营闭环

目标：

- 建立一周尺度的巩固和反馈

交付物：

- 周报聚合逻辑
- 周测题目生成逻辑
- 错题回流 `review_items`
- 后台手动触发与发送日志

完成标准：

- 周报和周测能基于日快照而不是重新扫全量消息
- 错题能进入复习链路

- [ ] `message_delivery_logs` 至少有 1 条周报或周测发送记录
- [ ] 后台可查到任务执行记录和发送日志

## 10. 风险与对策

### 风险 1：LLM 分析成本和延迟过高

对策：

- 白天只做轻量规则标注
- 晚上按“用户 x 日期”批量总结
- 为晚间卡保留规则版降级输出

### 风险 2：卡片内容过长，群体验差

对策：

- 学习包拆成清晰分区
- 晚间卡只保留高价值信息
- 超长自动分页或合并转发

### 风险 3：次日回捞过多，增加学习负担

对策：

- 固定只回捞 3 个点
- 至少 1 个任务复用，不强制每题复用

### 风险 4：群配置来源混乱

对策：

- `config.yaml` 只做初始值
- 后台管理后，以数据库和运行时配置为准

## 11. 推荐执行方式

建议按“一个阶段一个 PR / 一个阶段一个测试闭环”推进，不要同时并行改数据库、Provider、卡片和后台。

推荐提交粒度：

1. `群聊采集与证据提取`
2. `词库与学习包`
3. `次日回捞`
4. `18:00 / 20:00 晚间闭环`
5. `周报与周测`
6. `后台运营与可观测性`

这样每一轮都能保持系统可运行，也方便你边看效果边调整产品规则。
